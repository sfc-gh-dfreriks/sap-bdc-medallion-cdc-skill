# Custom data products: CDC specification

This document specifies the four change-capture capabilities a custom SAP BDC data product needs, with the measured status of each on a reference tenant. Nothing here is generated by SAP automatically. The reader's job is to determine which capabilities the share already carries and which to request from the pipeline owner.

For the mechanism behind incremental capture, see [how-it-works.md](how-it-works.md). If your share carries standard data products instead of or in addition to custom ones, see [standard-products-cdc.md](standard-products-cdc.md).

![Custom track capabilities](https://raw.githubusercontent.com/sfc-gh-dfreriks/sap-bdc-cdc/main/assets/diagrams/D9_custom_track.png)

---

## What makes a product custom

A custom SAP BDC data product is one where the pipeline owner, not SAP, chose what change-tracking columns to include. SAP does not generate `__OPERATION_TYPE`, `__TIMESTAMP`, or the `load_type_<hash>` / `run_id_<hash>` columns on these objects. The only change signal present is whatever the pipeline owner added - typically a replication timestamp written by the SLT layer.

The reference tenant carried 4 catalog-linked databases, 23 objects, and 1,825 columns. All 23 objects carried `ZZLASTCHGDATE`. Account-wide, 59 objects carry it. No object carried a per-row operation code.

---

## The four capabilities

| Capability | Status on reference tenant | Action required |
| --- | --- | --- |
| Change timestamp | Present and usable | Verify column name; require NOT NULL |
| Business deletion and blocking codes | Present but discarded | Surface in Gold layer - costs nothing |
| Replication operation code | Absent - must be requested | Request from pipeline owner or accept row-count reconciliation only |
| Load-phase flag | Optional - inferable without it | Request only if convenient to pipeline owner |

---

## Capability 1: Change timestamp

**Status: present and usable.**

On the reference tenant, the replication timestamp column `ZZLASTCHGDATE` was present on 23 of 23 L1 objects. Type: `TIMESTAMP_NTZ(6)`. Zero nulls across every measured object:

| Object | Row count | Null `ZZLASTCHGDATE` |
| --- | --- | --- |
| GL line items | 108,615,680 | 0 |
| Purchase order items | 4,314,292 | 0 |
| Secondary object | 1,073,135 | 0 |

This column is strictly better than the standard-track equivalent (`__TIMESTAMP`). It is correctly typed as `TIMESTAMP_NTZ` rather than TEXT, carries no comma decimal separator, and has full coverage on all measured objects. Do not accept the `__TIMESTAMP` TEXT-with-comma form from the standard track as a substitute on this track - that would be a regression.

**Pruning performance.** On a 108,615,680-row GL object (7,035.80 MB), a watermark predicate scanned 0.00 MB in 47-79 ms. A full read of the same object scanned 7,035.80 MB. A business-date predicate on the same object scanned 4,695.75 MB for 549 matching rows. The replication timestamp prunes because the BDC connector writes it in monotonic, non-overlapping batches - Iceberg per-file statistics eliminate every file that cannot contain a match. A business date does not prune because documents from many periods land in the same files. See [how-it-works.md](how-it-works.md) for the mechanism.

**Connector merge verified.** Over five observed days on the reference tenant: 108,615,638 rows across 402 Parquet files on initial load, then 10 rows in 1 new file on day 2, then 20 rows in 1 new file on day 3. Historical rows kept their original timestamps throughout. The connector merges; it does not reload. 5 distinct write days, with 100.0000% of rows on the initial load and small incremental additions since. This merge behaviour is the precondition for pruning to be effective.

**Engine verified end to end.** Initial dynamic table refresh: 4,314,292 rows in 18.3 s. Subsequent no-change refresh: `NO_DATA` in 984 ms. 10 of 10 Gold dynamic tables confirmed `INCREMENTAL` after pinning `REFRESH_MODE`. Batch windows observed: approximately 06:25 for procurement objects, approximately 14:25 for finance and sales.

**Column name discovery.** The name `ZZLASTCHGDATE` is specific to the reference pipeline configuration. It is a customer extension field, not a BDC standard. The name may differ between products on the same tenant or be absent on a deployment that was not configured to include it. Run the readiness probe to discover the actual column name:

```bash
python3 cdc_readiness.py --connection <your_connection> --report readiness.md
```

A match produces: `signal.watermark: Replication timestamp present on all 23 objects (column: ZZLASTCHGDATE)`.

**What to specify.** Require the column `NOT NULL` in any data product agreement. Confirm it reflects the connector write time, not a business event date. A business date such as `PostingDate` or `DocumentDate` is not a replication watermark.

## Capability 2: Business deletion and blocking codes

**Status: present but discarded.**

Standard SAP business objects carry logical deletion indicators as ordinary data columns. On the reference tenant, these columns exist in the data product but the Gold layer carries no filter on them and no copy of the columns themselves.

**Measured on purchase order items (`PURCHASINGDOCUMENTDELETIONCODE`), USD scope only:**

| Code | Meaning | Row count | Ordered value (USD bn) |
| --- | --- | --- | --- |
| blank | Active | 3,494,547 | 40.17 |
| L | Delivery completed | 812,913 | - |
| S | Statistical delivery completed | 6,831 | - |
| X | Item blocked | 1 | - |
| **Flagged total** | L + S + X combined | **819,745 (19.0%)** | **29.33 (42.2%)** |
| **Grand total** | all rows | **4,314,292** | **69.50** |

The Gold purchase order table carries all 4,314,292 rows - the same count as the source - with no deletion column and no filter. The 29.33 bn flagged ordered value flows into Gold labelled as active spend. The 69.50 bn headline figure is the same number the Gold layer reports; the USD scope means the components are additive.

**Additional deletion columns on the reference tenant:**

| Object type | Column | Flagged row count |
| --- | --- | --- |
| Purchase order headers | `PurchasingDocumentDeletionCode` | 1,594 |
| Product master | `IsMarkedForDeletion` | 1,086 |
| Supplier master | `DeletionIndicator` | present |
| GL account master | `AccountIsMarkedForDeletion` | present |
| Supplier central | `SupplierCentralDeletionIsBlock` | present |

**Caveats.**

- These are business deletion flags, not replication operation codes. A row physically removed from the source still leaves no trace in the data regardless of these columns.
- Whether L and S purchase order items belong in spend analysis is a business decision. Carrying them unlabelled and unfiltered is not defensible once you know they are there.
- The USD-scope figures are additive because spend was measured in a single currency. Cross-currency totals require exchange rate adjustment.

**Action required.** Surfacing these columns in the Gold layer is free and requires nothing from SAP or the pipeline owner - the columns already exist in the data product share. Add them to the dynamic table select list and include the appropriate filter in consuming views. This is the highest-value action available on this track. It requires no coordination, no pipeline change, and no wait.

**What to verify with the pipeline owner.** Confirm that the columns listed above are included in the share for the relevant objects. On the reference tenant they were present. On a tenant where any are absent, request their inclusion by column name.

## Capability 3: Replication operation code

**Status: absent - must be requested.**

The custom-track share carries no column that distinguishes insert, update, and physical delete at row level. There is no `ODQ_CHANGEMODE`, `RECORDMODE`, `UPDKZ`, or equivalent. When a row is physically removed from the source, it disappears from the share without leaving any trace. The watermark window will never encounter the deletion. Dynamic tables handle this by diffing consecutive source snapshots - the absence of a row in snapshot N+1 is the signal - which is the primary reason dynamic tables are the recommended engine on both tracks.

**On the standard track.** `__OPERATION_TYPE` exists on standard data product objects, which makes delete detection structurally possible on that track. However, no delete code was observed on the reference standard-track share (67,480 rows across 5 objects). Whether the standard track satisfies this requirement in practice is also unverified as of the reference measurement.

**What to request.** Either of the following closes this gap for the watermark exception path:

1. A per-row operation code column distinguishing insert, update, and physical delete on every shared object - equivalent to `RECORDMODE` or `ODQ_CHANGEMODE` in classic SAP delta queues. Typically added as an SLT extension field and specified to the pipeline owner before the data product is configured.
2. A written commitment from the data product owner that the data product never physically removes rows and that all logical deletions are represented via the business deletion flags in Capability 2 above. This commitment must be per data product, not per source system.

Without either, the only delete detection available on the watermark path is row-count reconciliation between source and target. Schedule the following query on a regular cadence regardless of which path you use:

```sql
SELECT OBJECT_NAME, SOURCE_COUNT, TARGET_COUNT,
       TARGET_COUNT - SOURCE_COUNT AS DIVERGENCE
FROM   <L2_DB>.CAPTURE_CONTROL.VW_DELETE_RECONCILIATION
WHERE  TARGET_COUNT > SOURCE_COUNT;
```

A persistent positive divergence means physical deletes occurred upstream and the target has not absorbed them. Rebuild the target table. Identifying which specific rows were deleted is impractical on the watermark path.

**If deletes matter to you, do not settle for reconciliation.** The requests above are still worth making - a source-side operation code is the cleanest answer and benefits every consumer of the data product - but you are not blocked while you wait for one. Put a dynamic table over the share and a standard stream on that dynamic table: the dynamic table detects the delete by diffing snapshots, and the stream exposes it as a `DELETE` record with `METADATA$ACTION` and `METADATA$ROW_ID` populated, so you know *which* rows went. This requires nothing from the pipeline owner and works on the custom track despite the missing operation column. It has been validated with a customer. Reconciliation then becomes a safety net rather than your only delete signal.

The one thing it does not give you is an update flag - `METADATA$ISUPDATE` is always `FALSE`, so an update arrives as a `DELETE` + `INSERT` pair for the same key. Write the MERGE so that pair converges correctly rather than depending on the flag. Full pattern and caveats: [how-it-works.md](how-it-works.md#the-interposition-that-does-work-a-stream-on-a-dynamic-table).

## Capability 4: Load-phase flag

**Status: optional - inferable without it.**

A declared load-phase flag explicitly marks which rows arrived on the initial load and which are incremental deltas. On the reference tenant, this is inferable from the `ZZLASTCHGDATE` distribution alone:

| Day | Row count |
| --- | --- |
| Initial load day | 4,314,285 |
| Day +1 | 6 |
| Day +2 | 1 |

The pattern is unambiguous. Rows with the load-day timestamp are the initial load; rows with later timestamps are deltas.

The standard-track equivalent (`load_type_<hash>`) provided `initial` = 67,087 and `delta` = 393 on the reference share - the same partition by a more explicit route.

**When to request it.** If the pipeline owner can add a load-phase column at no additional cost, it eliminates the inference step and makes intent explicit in the data. It is not required for capture to work correctly and should not be a blocking request.

## What to hand a pipeline owner

These four items structure the conversation with the pipeline owner or SAP BDC contact. They are not a product specification; they are a prioritised request list.

1. **Change timestamp (already present - verify).** Confirm the column name on your tenant and that it will remain `NOT NULL` in future product versions. Confirm it reflects the connector write time, not a business event date. Request the name be documented in the data product metadata.

2. **Business deletion columns (already present - verify inclusion).** Confirm that `PurchasingDocumentDeletionCode`, `IsMarkedForDeletion`, `DeletionIndicator`, `AccountIsMarkedForDeletion`, and `SupplierCentralDeletionIsBlock` are included in the share for the relevant objects. These cost nothing to surface and carry the highest immediate analytical value of the four capabilities.

3. **Replication operation code (absent - must be requested).** Request either a per-row operation code column (distinguishing insert, update, physical delete) on every shared object, or a written guarantee that the data product is soft-delete only. This is the most consequential gap and the most dependent on pipeline owner cooperation.

4. **Load-phase flag (optional).** If convenient to the pipeline owner, a column distinguishing initial load rows from delta rows. Lowest priority; defer if the conversation is already carrying items 1-3.

Focus the request conversation on items 2 and 3. Item 2 is already in the data and requires only confirmation; item 3 is the only one that requires pipeline configuration or a formal commitment.

## Registering for the watermark exception path

Where a dynamic table cannot serve (non-deterministic transformation, or target outside Snowflake), register custom-track objects in the `WATERMARK` control table with `TRACK = 'CUSTOM'`:

```sql
INSERT INTO <L2_DB>.CAPTURE_CONTROL.WATERMARK
  (OBJECT_NAME, SOURCE_FQN, TRACK, WATERMARK_COLUMN, MERGE_KEY_COLUMNS,
   OPERATION_COLUMN, LAST_WATERMARK)
SELECT '<NAME>',
       '"<LINKED_DB>"."<LINKED_SCHEMA>"."<OBJECT_NAME>"',
       'CUSTOM',
       'ZZLASTCHGDATE',
       '<KEY_COLUMN_1>,<KEY_COLUMN_2>',
       NULL,
       NULL
WHERE  NOT EXISTS (SELECT 1 FROM <L2_DB>.CAPTURE_CONTROL.WATERMARK
                    WHERE OBJECT_NAME = '<NAME>');
```

`TRACK = 'CUSTOM'` is required. The `WATERMARK` table has a CHECK constraint; an insert with any other value fails with error 23514. `WATERMARK_COLUMN` must match the actual column name found by the probe on your tenant. `OPERATION_COLUMN` is NULL on this track - there is no operation column. The watermark procedure path is in `sql/04_watermark_exception_path.sql`.
